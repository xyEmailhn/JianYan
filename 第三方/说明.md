# 第三方库

这里放的是**已经 vendor 进来**的 C 库：源码直接躺在仓库里，不靠包管理器，
不要求联网，`make` 一下就能用。

这么做的理由很简单：简言的后端是「生成 C，交给 gcc」。要加能力，最省事的
办法不是自己重写一遍 PNG 编解码，而是把别人写好、被用过几百万次的那份拿过来。

## 里面有什么

| 目录 | 库 | 版本 / 提交 | 许可证 | 用来做什么 |
|---|---|---|---|---|
| `stb/` | [nothings/stb](https://github.com/nothings/stb) | `6b5799b` | MIT / 公共领域 | 读图（PNG/JPG/BMP/TGA/GIF/PSD/HDR）、写图、字体光栅化、矩形装箱 |
| `nanosvg/` | [memononen/nanosvg](https://github.com/memononen/nanosvg) | `239e102` | zlib | 解析并栅格化 SVG |
| `tommath/` | [libtom/libtommath](https://github.com/libtom/libtommath) | `45402fd` (v1.3.0) | 公有领域 | 任意精度整数 |
| `mpdec/` | [mpdecimal](https://www.bytereef.org/mpdecimal/)（CPython v3.13.0 内嵌副本） | v3.13.0 | MIT | 十进制高精度浮点 |
| `dr/` | [mackron/dr_libs](https://github.com/mackron/dr_libs) | `e381981` | 公有领域 / MIT-0 | WAV 读写、MP3 解码 |

只保留真正用到的头文件，`stb` 里另外几十个文件（图像缩放、压缩、音频）没有拿。

三个"大件"的取舍：

- **libtommath 而不是 GMP**：GMP 是 LGPL，静态链接进分发物有连带义务。
  libtommath 公有领域、mpdecimal MIT，都"随便用"。性能差一点，
  但算 1000! 只花 0.01 秒，用户感觉不到。
- **mpdecimal 的 `pyconfig.h`**：CPython 的副本要求外部提供这个头，这里补了
  `CONFIG_64` / `ANSI` / `HAVE_UINT128_T` / `HAVE_UINT64_T` 四个宏，
  **没有改动第三方源码**。少任何一个，性能掉一个数量级；`CONFIG_64` 少了会算错。
- **dr_wav + dr_mp3 而不是 miniaudio**：miniaudio 是 5 MB 单头文件，功能全，
  但沙箱里没有声卡，**播放那一半一行都验证不了**。验证不了的东西不进语言。

`utf8proc`、`mimalloc`、`miniaudio` 都拉下来看过，**没有留下**，理由在下面「试过但没要」。

## 怎么接的

关键在于**不要把第三方代码塞进生成的 `.c`**。

`stb_image.h` 展开实现后是二十多万行。如果每个 `.jy` 程序编译时都带一遍，
编译时间会从 30 毫秒涨到一秒多，而大多数程序根本不碰图片。

所以分成两半：

```
第三方/运行库.c   ←→  编译一次  →  第三方/lib简言图.a   (321 KB)
                                        ↑
生成的 .c 里只有：extern unsigned char *简_图_载(...);  几行声明
```

生成代码里只有声明，实现在静态库里。链接时按需取用——不碰图片的程序，
连那 321 KB 都不会进二进制。

`简编译` 会在自己所在目录附近找 `lib简言图.a`（`../第三方/`、`./`、`./第三方/`
三个位置都试），找不到就退化成不链接：纯计算程序照样能编，用到 `图` 的时候
才会在链接阶段报 `undefined reference`，错误信息里会告诉你回 `第三方/` 跑 `make`。

```bash
cd 第三方 && make        # 一次性，约 3.5 秒
```

## 接口边界

运行时库**不认识**语言里的 `简图` 结构体。所有函数只收「像素指针 + 宽 + 高」：

```c
unsigned char *简_图_载(const char *路径, long long *宽, long long *高, char *错);
int            简_图_存(const char *路径, const unsigned char *像素, long long 宽, long long 高);
unsigned char *简_图_新(long long 宽, long long 高);
unsigned char *简_图_缩(const unsigned char *源, long long 宽, long long 高, long long 新宽, long long 新高);
long long      简_图_写(unsigned char *画布, long long 宽, long long 高, long long x, long long y,
                       double 字号, const char *文字, long long 长, long long 颜色);
double         简_图_量(const char *文字, long long 长, double 字号);
```

这样两边没有共享头文件，谁先编都行，`简图` 的字段将来怎么改也不会波及这个库。

像素格式统一 **RGBA8、行紧凑、左上角原点**。`stbi_load` 的第四个参数写 4，
让 stb 在入口处做一次通道转换，比每个调用点都判断通道数省事。

## 试过但没要

### mimalloc —— 没有性能收益

把 `src/static.c` 编成 `.o`，用 `-DMI_MALLOC_OVERRIDE=1` 覆盖 `malloc`，
链进一个 30 万次字符串拼接 + 100 万次数组追加的基准：

| | 时间 | 峰值内存 |
|---|---|---|
| glibc malloc | 0.02 秒 | 37 MB |
| mimalloc | 0.03 秒 | 42 MB |

**更慢，而且更占内存。**

原因不在 mimalloc，在简言的运行时：字符串拼接、数组扩容出来的旧内存从来不释放。
分配器再快也只是分配快，这个负载的瓶颈根本不在分配路径上——glibc 的 tcache
处理这种「一路分配不释放」的模式已经够快了。mimalloc 的优势在多线程、
高碎片、频繁 free/alloc 的场景，那正是简言现在没有的。

真要提速，该改的是运行时（引用计数或者区域回收），不是换个分配器。
所以删掉了，不 vendor。

### miniaudio —— 有一半验证不了

5 MB 的单头文件，解码、混音、声卡枚举、实时播放全都有。

问题是沙箱里**没有声卡**。解码这一半我能逐样本验，播放那一半只能"写完就交"，
连"有没有声音"都答不上来。把验证不了的能力写进语言，等于给用户埋一个
"我这能跑、你那不一定"的坑。

dr_wav + dr_mp3 加起来 540 KB，只做"文件 ↔ float 数组"这一件事，
而这件事的每个环节都能对着 `ffprobe` 交叉验证。

### utf8proc —— 太大了

2.4 MB 的 Unicode 数据表，换 `大写`/`小写` 的正确性。当前实现只处理 ASCII，
对中文（本就没有大小写）没影响。等真要做土耳其语、德语 ß 这类，
再拉回来不迟，没必要现在让仓库胖 2.4 MB。

## 保真度说明：SVG 读取

`nanosvg` 能解析路径、变换、实心填充、线性/径向渐变、虚线，但**不支持**：

- 渐变蒙版（`mask`）
- 滤镜（`filter`，模糊、阴影）
- `clip-path` 的复杂情形
- CSS 类（只认 `style` 属性和表现属性）

实际表现：简言自己画的那张海报，读回来山、海、船、太阳都在，但天空里几层
`stop-opacity` 柔化的渐变会露出硬边，看着像多了几道雾带。

**这不是 bug，是能力边界。** 要像素级还原就用浏览器或 `cairosvg`；
把 SVG 当"能读的图形格式"用（图标、logo、简单矢量图）则完全够。

顺带修了一个真实的坑：`objectBoundingBox` 下写 `x2="1"` 这种无单位数，
规范里是「1 个包围盒单位」，但 nanosvg 当成 1 像素，整个渐变挤在一个像素里。
写 `100%` 就没有歧义。`示例/绘图.jy` 已经统一改成百分比。
