# 语法分析器说明

> 这份文档假设你**完全没学过编译原理**，也没写过 C。
> 读完你会知道：语法分析在干什么、这 1700 行代码怎么读、为什么它这么快、以及它现在还不能做什么。

---

## 一、它在干什么

词法器把源码切成一个个词：

```
整数 甲 = 1 + 2 * 3
↓
[整数] [甲] [=] [1] [+] [2] [*] [3]
```

但词排成一排，**看不出谁先算**。`1 + 2 * 3` 到底是 `(1+2)*3` 还是 `1+(2*3)`？光看这一排词，机器不知道。

语法分析器干的事，就是把这些词**按层次叠起来**：

```
变量 甲
  类型 整数
  二元 +
    整数 1
    二元 *
      整数 2
      整数 3
```

`*` 在 `+` 下面，意思是"先算乘法"。这棵树叫**语法树**（AST）。

### 为什么非要树不可

因为后面所有工作都要在树上走：

| 后面要做的事 | 在树上怎么做 |
|---|---|
| 检查类型对不对 | 看 `+` 的两边是不是数字 |
| 算出常量 | 从叶子往上算 |
| 生成机器码 | 后序遍历，先算孩子再算爹 |
| 报错指到具体位置 | 每个节点都记着自己在第几行第几列 |

如果只有一排词，这些事一件也做不了。

## 二、先看结果

```bash
make            # 编译
./简语法 ../词法/示例/词频.简
```

输出（节选）：

```
程序
  模块 词频
  引入 std.io
  结构 词频项
    字段 词
      类型 字符串
    字段 次数
      类型 整数
  函数 统计
    参数 文本 [借用]
      类型 字符串
    类型 映射[字符串, 整数]
    块
      变量 表 [私有]
```

怎么读：

- **缩进两格 = 我是上面那个的孩子**。`字段 词` 和 `字段 次数` 都是 `结构 词频项` 的孩子。
- 行首的中文是**节点种类**（这是函数、这是变量、这是加法）。
- 后面跟的是**名字或原文**（函数叫 `统计`，变量叫 `表`）。
- 方括号里是**标记**，比如 `[借用]` 表示这个参数是借用来的，`[私有]` 表示只在本函数里可见。

## 四、核心手法：递归下降

规则怎么写，代码就怎么写。语法规范里写：

```
如果语句 = "如果" 表达式 "就" 块 { "否则如果" 表达式 "就" 块 } [ "否则" 块 ]
```

代码就是：

```c
static 节点 *解析如果(语法器 *P)
{
    吃(P);                              // 吃掉"如果"
    加子(n, 解析表达式(P));              // 要一个表达式
    期望关(P, "就", "...");              // 必须看到"就"
    加子(n, 解析块(P));                  // 要一块代码
    while (词是关(当前(P), "否则如果")) { ... }   // 后面还有就继续
    if (词是关(当前(P), "否则")) { ... }
}
```

一句对一句，没有魔法。**"吃"就是往后挪一个词**，`期望关` 就是"必须看到这个词，否则报错"。

### 优先级怎么处理

这是唯一需要动点脑筋的地方。办法是：**给每一级优先级写一个函数，低的调用高的**。

```
解析加法 → 解析乘法 → 解析一元 → 解析幂 → 解析后缀 → 解析基本
```

遇到 `1 + 2 * 3` 时，调用链是这样的：

```
解析加法 要一个"乘法"
  解析乘法 要一个"一元"
    解析一元 要一个"幂"
      解析幂 要一个"后缀"
        解析后缀 → 基本 → 拿到 1
      看到 +，不是 ^，返回 1
    看到 +，不是乘号，返回 1
  加法函数现在手里有 1，看到 +，吃掉
  再要一个"乘法" → 这次拿到 2 * 3（乘法函数自己把 * 吃掉了）
  于是树变成 1 + (2 * 3)
```

一句话记：**函数调得越深，绑得越紧**。乘法的函数在加法里面，所以先结合。

`^`（乘方）是右结合，`=`（赋值）也是右结合，这两个特殊：它们递归调用**自己**，而不是调用下一级。

## 五、完整优先级表（和代码一一对应）

| 级 | 运算符 | 函数 | 结合 |
|---|---|---|---|
| 1（最松） | `=` | `解析赋值` | 右 |
| 2 | `..` | `解析拼接` | 左 |
| 3 | `或` | `解析或` | 左 |
| 4 | `与` | `解析与` | 左 |
| 5 | `\|` | `解析位或` | 左 |
| 6 | `^^` | `解析位异或` | 左 |
| 7 | `&` | `解析位与` | 左 |
| 8 | `==` `!=` | `解析相等` | 左 |
| 9 | `<<` `>>` `<=` `>=` | `解析比较` | 左 |
| 10 | `<<<` `>>>` | `解析移位` | 左 |
| 11 | `+` `-` | `解析加法` | 左 |
| 12 | `*` `/` `//` `%` | `解析乘法` | 左 |
| 13 | `非` `!` `#` `~~` `-`(一元) `+`(一元) | `解析一元` | 右 |
| 14 | `^` | `解析幂` | 右 |
| 15（最紧） | `()` `[]` `.` | `解析后缀` | 左 |

验证一下代码里的表（`二元层` 在 Python 版里更直观）：

```python
二元层 = [
    ("拼接", [".."], "或"),
    ("或", ["或"], "与"),
    ...
    ("乘法", ["*", "/", "//", "%"], "一元"),
]
```

从左到右就是从松到紧。改优先级只需要动这张表的顺序，不用改任何逻辑。

## 六、报错是产品的一部分

编译器最让人恼火的不是"报错"，而是**报错说不清在哪儿**。所以这里每条错都回答三个问题：

```
示例/覆盖.简:20:18: 语法错误：这里应该写 `{`（一块代码要用 { 开头），实际是 换行
  20 |     函数 面积() -> 浮点
                                    ^
```

| 问题 | 答案 |
|---|---|
| 哪儿错了 | `20:18`，还把第 20 行**原文抄出来**，底下画 `^` |
| 错在什么 | "这里应该写 `{`" |
| 实际看到啥 | "实际是 换行" |

几个真实例子：

```
函数 甲(a: 整数) -> 整数 {
    如果 a << 0 {          ← 少了"就"
```

```
语法错误：这里应该写 `就`（`如果` 的条件后面要写 `就`），实际是 `{`
  4 |     如果 a << 0 {
                        ^
```

```
    私有 整数 b = a +      ← 加号后面没东西
```

```
语法错误：这里需要一个表达式，但这一行已经结束
  7 |     私有 整数 b = a +
                                ^
```

```
模块 测试                   ← 用了关键字当名字
```

```
语法错误：这里需要一个名字（模块路径），但 `测试` 是语言保留的关键字，不能当名字用
```

### 为什么不会连环报错

出一次错以后，解析器会**跳到这一行末尾**再继续。所以缺一个括号只会报一次，不会牵连后面十行。

如果某一行死活解析不动（一个词都没吃掉），它会报"这一句看不懂，已跳过"然后强行吃掉一个词——**保证不会死循环**。

## 七、为什么这么快

实测：8.4 MB 源码、216 万个词、每轮 104 万个节点。

| 版本 | 体积 | 吞吐 | 每秒词数 |
|---|---|---|---|
| `-O0`（调试） | 120 KB | 35.4 MB/s | 930 万 |
| `-O3 -flto` | 84 KB | **68.6 MB/s** | **1798 万** |
| musl `-Oz` 静态 | **66.5 KB** | 35.2 MB/s | 924 万 |
| musl `-O3` 静态 | 87 KB | 41.8 MB/s | 1096 万 |
| Python 参考实现 | — | 1.26 MB/s | 30 万 |

作为对照：GCC 解析 C 代码约 1–5 MB/s，Clang 约 10–20 MB/s。**68 MB/s 属于很快的一档**。

快的五个原因，每一条都能在代码里指出来：

| 原因 | 在哪儿 | 省了什么 |
|---|---|---|
| 先把所有词切进数组 | `切好所有词` | 解析时不再回头扫源码，往前看只是读下标 |
| 只往前看，不退回去 | 全篇只有一处回溯（`是函数类型声明`） | 不用保存/恢复状态，不用建索引 |
| 每个词只记"从哪儿开始、多长" | `指文字` | 全程不复制字符串，不 malloc |
| 节点一次分配、孩子数组翻倍扩容 | `新节点` `加子` | 平均每个孩子只搬一次家 |
| 没有虚函数、没有异常、没有 GC | 全篇 | 没有隐藏开销 |

> 还能更快：把节点改成"一整块内存里排队分配"（arena），能省掉每个节点一次 malloc。
> 现在没这么做，是因为它会让人多一层"这块内存在哪儿"的心智负担，不值得。
> 66 KB / 68 MB/s 已经够用了。

## 八、它现在还不能做什么

诚实列出来，免得你以为它能直接跑程序：

| 限制 | 说明 | 以后怎么办 |
|---|---|---|
| 不检查名字重不重复 | `整数 a = 1` 写两遍不报错 | 下一棒：符号表 |
| 不检查类型 | `1 + "字符串"` 能过 | 下一棒：类型检查 |
| 不检查泛型约束 | `[T: 可比较]` 只是记下来 | 类型检查时验证 |
| 结构体字面量只能无名 | 写 `{ 1, 2 }`，不能写 `点{ 1, 2 }` | 加 `新建` 关键字，或规定条件里必须加括号 |
| 匹配的模式只存文本 | `例 失败(原因):` 里 `原因` 没单独拎出来 | 类型检查时展开 |
| 不检查 `打断` 在不在循环里 | 写哪儿都行 | 语义分析 |
| 外部函数名不能是关键字 | `外部 函数 关闭` 报错，得写 `关闭文件` | 语言规则如此，报错里会说清 |

前三条属于"下一棒"的活，不是这一棒的漏洞。后四条是**设计决定**，都写进了规范。

## 九、它和词法器的关系

`parser.c` 第一行有效代码是：

```c
#define 简_只要词法 1
#include "../词法/lexer.c"
```

意思是：**把词法器整个搬进来用，但不要它的主函数**。

好处是词法规则只有一份。哪天改了"什么算关键字"，语法器自动跟着变，不会出现"词法器认为是关键字、语法器认为是名字"这种鬼事。

代价是编译时要连词法器一起编（`make` 已经处理好），以及两个文件不能有重名的全局函数。对这个小项目来说，这个代价很划算。

## 十、怎么验证它没写错

一条命令：

```bash
make 对答案
```

它做三件事：

1. C 版解析 `词频.简`，输出一份树
2. Python 版（`parser_参考实现.py`，规则一样、写法更直白）解析同一个文件
3. `diff` 两份输出

```
两份实现输出完全一致
```

**两种语言、两套代码、同一个结果**，是目前能拿到的最强证据。改规则时先跑这个，比肉眼检查靠谱。

另外 `示例/覆盖.简` 是专门写的"语法覆盖测试"：153 行里把模块、引入、泛型、结构、枚举、三种接口写法、实现、外部、测试、编译期、宏、异步、线程、通道、匹配、两种 `对`、四种声明、全部运算符都写了一遍。**它必须零错误通过**。

## 十一、下一步

语法树有了，接下来是**符号表 + 类型检查**：

- 建一张表记下每个名字是什么（变量？函数？类型？）
- 走一遍树，检查每个名字有没有定义、类型对不对
- 报错要能说"第 12 行的 `甲` 是 `字符串`，不能加到 `整数` 上"

到那一步，"语法对不对"就升级成"意思对不对"了。
