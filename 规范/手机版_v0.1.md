# 手机版：把简言装进安卓

> 这一份讲的是 `手机/` 目录：为什么最后走了「解释执行」，解释器的值模型长什么样，
> 以及为了让它和桌面后端算得一样，做了哪些对拍。

## 1. 三条走不通的路

「把编译器搬到手机上」听上去是交叉编译一下的事。实际动手，三条直路都堵着：

| 想法 | 为什么不行 |
|---|---|
| 把 `简编译` 交叉编译成 arm64 可执行 | Android 上没有 gcc，也没有 as/ld；C 后端最后一步是调 `gcc`，原生后端最后一步是 `as` + `ld` |
| 用原生后端自出 arm64 ELF | 自出 ELF 那段只认 x86-64。改 arm64 等于重写整个指令选择与寄存器分配 |
| 编出 .so，运行时 `exec` 私有目录里的程序 | Android 10（API 29）起对应用私有目录做了 W^X 限制，targetSdk ≥ 29 直接拦 |

最后一条常被忽略：`adb shell` 里手动跑得好好的，装成 App 就 `Permission denied`。
这不是权限没申请，是系统策略。

所以只剩解释执行：**不生成机器码，直接按 IR 一条条算**。与 CPU 无关，
也就与 arm64 / x86 无关。

## 2. 解释器复用前端，不重写语言

`手机/解释.c` 的第一行是：

```c
#define 简_只要中间 1
#include "../中间/ir.c"
```

`ir.c` 又整份 include 了 `语义/sema.c`，后者 include `语法/parser.c`、`词法/lexer.c`。
于是手机版拿到的诊断信息、类型检查、借用检查、常量折叠，与桌面**是同一份代码**。

这条决定省掉的最大麻烦不是代码量，而是**两边报错不一致**。教学场景里，
手机上看到的错误和电脑上看到的必须是同一句。

## 3. 值模型：为什么不能照抄 C 后端的定宽结构

C 后端里，每个值在生成代码时都有确定类型，因此可以直接用 C 的结构体：
`简字` 是 16 字节、`简组` 是 32 字节、结构体按字段排布。

解释器不行：一个槽位在执行前不知道会装什么。所以值是一个带标签的联合：

```c
typedef struct {
    int 种;          /* 型_整数 / 型_浮点 / 型_字符串 ... */
    long long i;
    double f;
    解串 *字;
    解组 *组;
    解映 *映;
    void *p;         /* 结构、变体、结果 */
} 解值;
```

代价是每个值 48 字节、每次 `载`/`存` 整体拷贝。收益是**不必复刻布局计算**：
不需要知道 `简组` 的元素宽度、不需要知道结构体字段偏移。

浮点单独一个 `f` 而不是塞进 `i` 按位转，是因为 C 的 `double` 与 `long long`
在联合里共用一块内存时，写法稍不注意就会踩到严格别名。

## 4. 容器：故意选了慢的那一种

| 类型 | C 后端 | 解释器 | 理由 |
|---|---|---|---|
| 组 | 连续字节数组 + 元宽 | `解值` 数组 | 元素天生异构，按字节搬反而要来回拷 |
| 映射 | 开放寻址哈希表 | 线性数组 | 教学程序的键数通常个位数，O(n) 够用，省一套哈希函数 |
| 结构 | 编译期算好的字段偏移 | 「名字 → 值」小表 | 不必复刻布局，也不怕字段改名 |

排序用的是插入排序，同样是因为 n 小。**先把语义跑对，性能是下一步的事**——
这句话在 v0.16 的浮点上用过一次，这里再用一次。

## 5. 隔离：fork 与步数闸

解释器里全是裸指针，用户代码是不可信的输入。两个保护：

**子进程执行。** JNI 层 `fork`，子进程把 stdout / stderr 都接到管道，
父进程一次读干。子进程段错误只死自己，App 还能显示「程序异常终止：信号 11」。

```
App ──fork──> 子进程（跑解释器）──pipe──> App 显示
                    │
                    └─ 崩了也只崩这里
```

`bionic` 的 malloc 注册了 atfork handler，fork 后重新初始化锁，
所以子进程里继续 `malloc` 是安全的。

**步数闸。** 每执行一条 IR 指令计一次，超过两亿就报「运行太久了」并退出。
手机上写 `当 真 { }` 是很自然的事，没有这道闸，App 会变成一块砖。

## 6. 与桌面后端的对拍

解释器最容易骗自己的地方是「看起来对」。所以每次改完都跑三方对拍：

```
C 后端输出（gcc -O2）  ==  原生后端输出  ==  解释器输出
```

28 个用例里，解释器覆盖 22 个，原生后端覆盖 8 个。**22 个逐字一致**，
剩下 6 个（图片/声音/大数/并发/网络/链式）在手机版里是明确的「暂不支持」，
并且这个「不支持」本身也是受测行为：必须返回非零，并且说清楚是哪一块。

`手机/测试.sh` 分三层，第二层专测这个边界。

## 7. 三个只在真机上才会犯的错

### 7.1 字符串常量带着引号

IR 里 `q->文` 存的是**源码原文**，带引号、带 `\n` 这类转义。C 后端有个
`写字面量` 做反转义，解释器一开始直接把 `q->文` 当内容，于是 `打印行("你好")`
输出 `"你好"`。

修法是把 `写字面量` 的反转义那半边照抄一份。**两处必须逐字一致**，
否则同一个字符串在桌面和手机上长度都不一样。

### 7.2 零值结构没有字段表

`私有 矩形 r` 不写初值时，IR 给一条「常量 零值」。解释器一开始只把 `i` 置零，
没建字段表。于是后面 `r.左下 = ...` 找不到落点，报「结构里没有字段」。

修法是零值构造时按类型名去类型录里查字段，先把空表建出来。

### 7.3 APK 里没有 classes.dex

`d8` 把 dex 写在 `dex/classes.dex`，构建脚本 `cd` 到工作目录后 `zip classes.dex`
——目录里没有这个文件，`zip` 只打了一条警告，APK 照样签了出来。

**能装，点了就闪退。** 这类错误构建阶段不报错，只能在装包前把内容念一遍：

```bash
for f in classes.dex lib/arm64-v8a/libjianyan.so; do
    unzip -l "$APK" "$f" | grep -q "$f" || exit 1
done
```

## 8. 工具链

不用 gradle（会拉几百兆依赖），只用三样命令行工具：

| 步骤 | 工具 | 作用 |
|---|---|---|
| 交叉编译 | NDK 的 `aarch64-linux-android23-clang` | 出 `libjianyan.so`（209 KB） |
| 资源与清单 | `aapt2 link` | manifest + assets → 基础包 |
| Java → dex | `javac` + `d8` | 3.2 KB 的 `classes.dex` |
| 对齐 | `zipalign -f 4` | 4 字节对齐 |
| 签名 | `apksigner` | v1 + v2 签名 |

产物 **112 KB**：`assets/index.html` 7.6 KB + `classes.dex` 3.2 KB
+ `libjianyan.so` 209 KB（压缩后约 100 KB）。

## 9. 能力边界

手机版不是「简言的完整实现」，是一个**教学用执行器**。明确不接的：

- **图片、声音**：需要渲染后端与音频设备，且 v0.4 那套渲染器在 C 后端里是
  生成代码的一部分，解释器要接就得整份移植。
- **大数**：规范里是独立库，解释器没接。
- **线程、通道**：要 pthread，fork 出的子进程里开线程没有意义。
- **网络**：要 INTERNET 权限与事件循环，且不适合放在「跑一下」的交互里。

遇到这些，解释器输出 `手机版暂不支持这个内置函数：X` 并返回非零。
**报错比算错好**——这是这个项目从 v0.15 起一直守的一条线。
