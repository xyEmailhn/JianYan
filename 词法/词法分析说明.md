# 简言 · 词法分析器说明

> 这份文档假设你**完全没写过编译器**，也**没学过 C**。
> 读完你应该能：说清词法分析在干什么、看懂 `lexer.c` 的每一个函数、知道它为什么快。

---

## 一、它到底在干什么

编译器把源码变成程序，要分好几步，第一步就是**词法分析**（也叫"分词"）。

它的工作只有一件：**把一串字符，切成一个个有意义的"词"，并告诉后面的程序每个词是什么类型。**

```
源码          整数  甲  =  1  +  2
              └┬─┘  └┬┘ └┬┘ └┬┘ └┬┘ └┬┘
切完          [整数] [甲] [=] [1] [+] [2]
              关键字 标识符 符号 整数 符号 整数
```

注意一个关键点：**切完之后，原始字符就没用了。**

后面的语法分析器只关心"这是个整数""这是个加号"，不关心它长什么样。这也是为什么词法分析器可以跑得飞快——它只扫一遍，看完就走，从不回头。

> 生活里的类比：把一句话切成词，标上词性。
> 「小明 吃 了 苹果」→ 名词 动词 助词 名词。
> 编译器后面要判断"这句话通不通"，但它先得有词。

## 二、一次完整的手工模拟

拿最短的一行代码走一遍，你就彻底懂了：

```
整数 甲 = 1 + 2
```

扫描器从最左边开始，一个字符一个字符往右挪。每一步它都在问同一个问题：**"从这个位置开始，我能读出什么词？"**

| 步 | 位置 | 看到 | 判断 | 动作 | 产出 |
|---|---|---|---|---|---|
| 1 | `整` | 汉字 | 名字的开头 | 一直往后吃，吃到空格停 | `整数` → 查表 → **关键字** |
| 2 | ` ` | 空格 | 空白 | 跳过 | 无 |
| 3 | `甲` | 汉字 | 名字的开头 | 吃到空格停 | `甲` → 查表 → 没查到 → **标识符** |
| 4 | ` ` | 空格 | 空白 | 跳过 | 无 |
| 5 | `=` | 符号 | 看一眼下一个是不是 `=` | 不是，所以只有一个字符 | **符号** `=` |
| 6 | ` ` | 空格 | 空白 | 跳过 | 无 |
| 7 | `1` | 数字 | 数字的开头 | 一直吃到不是数字 | **整数** `1` |
| 8 | ` ` | 空格 | 空白 | 跳过 | 无 |
| 9 | `+` | 符号 | 检查有没有 `++` 这种两字符符号 | 没有 | **符号** `+` |
| 10 | ` ` | 空格 | 空白 | 跳过 | 无 |
| 11 | `2` | 数字 | 数字 | 读完 | **整数** `2` |
| 12 | `\n` | 换行 | —— | —— | **换行**（简言用它当语句结束符） |

十二步，产出了 7 个词。整个 400 行代码，做的就是这十二步，只不过把"看到 X 该干什么"穷举完整了。

## 三、看代码前，先认识这 10 个 C 记号

代码是用 C 写的（因为要快）。但你不需要会 C，认识下面这些就够读懂了。

| 记号 | 中文意思 | 备注 |
|---|---|---|
| `int` | 整数 | 装一个数 |
| `char` | 一个字节 | 源码就是一个字节一个字节排着的 |
| `unsigned char` | 0～255 的字节 | 中文的一个字节可能大于 127，得用无符号的 |
| `const char *` | 一串字符的地址 | 读作"指向字符的指针"，你可以理解成"这段文字从哪开始" |
| `*`（在类型后） | 指针 | 不是乘法。`char *s` = 一段文字的起点 |
| `*`（在两数之间） | 乘 | |
| `&` | 取地址 | `&L` = "L 这个东西放在内存的哪个位置" |
| `->` | 顺着指针取成员 | `L->pos` = "L 指的那个东西的 pos 字段" |
| `.` | 取成员 | `t.长度` = "t 的 长度 字段" |
| `++` | 加一 | `i++` 就是 `i = i + 1` |
| `static` | 只在本文件里能用 | 相当于给函数加个"内部"标记 |
| `return` | 返回 | 交回结果，函数结束 |

还有一个概念：**函数**。`static int 是数字(unsigned char c)` 的意思是：

> 定义一个叫"是数字"的小工具，你给它一个字节，它还你一个整数（0 表示不是，1 表示是）。

代码里全是这种小工具，每个只干一件小事，然后拼起来。这是刻意的——**小函数好读，也好验证**。

## 四、代码地图：八个部分，按这个顺序读

`lexer.c` 从头到尾分成八块，我们用注释隔开了。**建议按 1 → 7 的顺序读，第 8 块（命令行）最后看。**

| # | 部分 | 干什么 | 大概行数 |
|---|---|---|---|
| 1 | 词的种类 | 定义"词"有哪 9 类，每类叫什么 | 30 |
| 2 | 关键字表 | 70 个关键字，以及怎么一秒查到 | 120 |
| 3 | 小工具 | "这个字是数字吗""这个字是汉字吗" | 60 |
| 4 | 往前走 | 维护"现在在第几行第几列" | 30 |
| 5 | 跳过空白和注释 | 把不要的东西扔掉 | 40 |
| 6 | 读各种词 | 读名字 / 读数字 / 读字符串 / 读符号 | 200 |
| 7 | **主循环** | **指挥上面所有函数，这是心脏** | 80 |
| 8 | 命令行 | 读文件、打印结果、跑性能测试 | 120 |

### 主循环只有 8 个分支

如果你只有五分钟，直接翻到 `下一个词()` 这个函数。它的骨架是：

```
只要还没到头：
    是空白？   → 跳过
    是注释？   → 跳过
    是换行？   → 吐一个"换行"
    是引号？   → 读字符串
    是数字？   → 读数字
    是字母/汉字？→ 读名字（顺便查一下是不是关键字）
    是符号？   → 读符号
    什么都不是？→ 报错，跳过这个字，继续
```

**整份代码就是这 8 句话的展开。** 别被 400 行吓到，剩下的都是"怎么把这 8 件事做对、做快"。

## 五、三个真正的难点

新手写词法分析器，90% 的坑在这三处。简言因为用中文关键字，还多一个坑。

### 难点 1：一个汉字是三个字节

文件里存的不是"字"，是**字节**。

```
"甲" 在文件里实际是：  E7 94 B2   （三个字节）
"abc" 在文件里是：     61 62 63   （三个字节，但是三个字）
```

所以"往后走一个字"这件事，对英文是走 1 字节，对中文是走 3 字节。走错了，就会把一个汉字劈成两半，后面全乱。

代码里的处理（`走()` 函数）：看第一个字节的大小，就知道这个字一共占几个字节：

| 首字节 | 这个字占 | 是什么 |
|---|---|---|
| `0x00`–`0x7F` | 1 字节 | 英文、数字、符号 |
| `0xC0`–`0xDF` | 2 字节 | 欧洲字母 |
| `0xE0`–`0xEF` | 3 字节 | **汉字**、全角符号 |
| `0xF0`–`0xF7` | 4 字节 | emoji |

还有第二个坑：**全角符号也是三字节**。`，`（全角逗号）和 `,`（半角逗号）长得像，但完全是两个东西。如果只按"三字节就当汉字"，那 `，` 会被当成一个汉字，混进标识符里，报出一堆莫名其妙的错。

所以代码里还有个 `是汉字()`，它把三个字节拼回一个编号（叫"码点"），再看这个编号在不在汉字的三个区间里：

```
U+4E00 – U+9FFF   常用汉字（两万多字）
U+3400 – U+4DBF   扩展 A（生僻字）
U+F900 – U+FAFF   兼容汉字
```

不在区间里 → 不是汉字 → 报错，并且给一句人话：

```
词法错误 3:6  这里用了全角符号，简言只认半角，应该写 (
```

> 这条提示是专门为中国用户写的。新手写中文代码，十个错误里有三个是全角符号，直接把正确答案告诉他，比让他去查文档强。

### 难点 2：最长匹配 —— `<<<` 不能拆成 `<<` 和 `<`

简言里，`<<` 是"小于"，`<<<` 是"左移"。

看到 `a <<< 2`，扫描器如果先匹配 `<<`，就会切成 `a << < 2`，意思全变了。

规则叫**最长匹配**：**能读长的就读长的，读不了再退短的。**

代码里的写法（`读符号()`）：

```c
case '<':
    长 = (s[0]=='<' && s[1]=='<' && s[2]=='<') ? 3     // 先试三个字符
       : (s[0]=='<' && (s[1]=='<' || s[1]=='=')) ? 2   // 再试两个
       : 1;                                            // 都不行就一个
```

同一套规则还管着这几对：

| 长的 | 短的 | 区别 |
|---|---|---|
| `<<<` 左移 | `<<` 小于 | |
| `>>>` 右移 | `>>` 大于 | |
| `^^` 按位异或 | `^` 乘方 | |
| `~~` 按位取反 | `~` 范围 | |
| `//` 整除 | `/` 除 | |
| `..` 拼接 | `.` 取成员 | |
| `->` 箭头 | `-` 减 | |

**顺序至关重要**：先试 3 个字符，再试 2 个，最后才 1 个。反过来就全错。

### 难点 3：`--` 是注释，`//` 是除法

C 语言里 `//` 是注释。简言把 `//` 定义成了**整除**，注释改用 `--`。

好处是 `x // 2` 这种"除以 2 取整"写起来和数学一样自然；代价是扫描器要分清楚：

| 看到 | 是什么 | 怎么判断 |
|---|---|---|
| `--` | 注释，吃到行尾 | 在主循环里**最先**判断，抢在符号之前 |
| `-` | 减号 | 不是 `--` 也不是 `->` |
| `->` | 箭头 | `-` 后面跟 `>` |
| `//` | 整除 | 在符号里按两字符处理 |
| `/` | 除 | |

顺序错了就会把 `x = a - -b` 当成注释，或者把 `// 2` 当成注释到行尾。代码里 `跳过注释()` 排在所有分支之前，就是为了抢这个先手。

## 六、为什么这么快

先说结论：**在这台机器上，它每秒能扫 5 亿字节的简言源码，一秒切出 1 亿个词。**

对比同一套规则、同一个输入，用 Python 写的教学版：**1.6 MB/s**。差 **300 倍**。

快的五个原因，按贡献从大到小：

### 1. 只扫一遍，从不回头

每个字节最多被看两次（一次判断开头，一次读完），看完就走。没有"先找一遍字符串在哪，再回头处理"这种事。

### 2. 不复制字符串

这是最容易被忽略的一条。朴素写法是：读到 `甲`，`malloc` 一块内存，把 `甲` 拷进去，存起来。

我们的写法是：**只记住"它在原文的第几个字节、有多长"**。

```c
typedef struct {
    词种类 种类;
    const char *起点;   // ← 只是原文里的一个位置，指向原文，不是拷贝
    int 长度;
    ...
} 词;
```

结果：**词法分析全程 malloc 次数 = 0**。没有内存分配，就没有锁、没有系统调用、没有碎片。

### 3. 中文整块跳过，不逐字节解码

判断"这是不是汉字"时，先看首字节范围（一次比较就否掉 95% 的情况），再解码校验。绝大多数字符一眼就处理完了。

读标识符时更直接：`L->pos += 3`，跳三个字节，不检查中间两个。

### 4. 关键字查表 O(1)

70 个关键字，如果用 `if (strcmp(文字,"如果")==0) ... else if ...` 一路比下去，最坏要比较 70 次，每次还要逐字节比。

改成哈希表：把关键字摊在 256 个格子里，算一次哈希就知道该去哪个格子找，**平均一次比较命中**。

启动时建表（`建关键字表()`，只跑一次，几微秒），之后每次查都是常数时间。

### 5. 没有函数指针、没有虚函数、没有异常

所有分支都是 `switch` 和 `if`，编译器能把它们编译成跳转表，CPU 分支预测器也学得会。C 里没有隐藏开销。

## 七、体积：36 KB，而且不依赖任何东西

同一个 `lexer.c`，换个链接方式，体积差 **20 倍**：

| 编译方式 | 体积 | 依赖 | 速度 |
|---|---|---|---|
| `gcc -O0`（调试） | 35 KB | glibc | 111 MB/s |
| `gcc -O2` | 27 KB | glibc | 440 MB/s |
| **`gcc -O3 -flto -s`** | **24 KB** | glibc | **502 MB/s** |
| `gcc -O3 -static`（静态） | 705 KB | 无 | 500 MB/s |
| **musl + `-Oz`（静态）** | **37 KB** | **无** | 413 MB/s |
| **musl + `-O3`（静态）** | **39 KB** | **无** | 483 MB/s |

两个要点：

1. **静态链接 glibc 是体积杀手。** 一旦 `-static`，glibc 会拖进来 700 KB。换 musl（一个为体积设计的 C 运行库），同样的静态可执行文件只要 37 KB，缩小 **19 倍**，而且拷到任何 Linux 上都能直接跑，不挑系统版本。

2. **`-s`（strip）去掉符号表。** 二进制里本来存着"每个函数叫什么名字、第几行"，这些只对调试有用，发布时全删掉，体积立减。

> 这正好对应语言设计里定的"编译产物不需要可逆性"：不保留源码、不内嵌语法树、不保证能反编译回简言代码。所以可以放心 strip、放心内联、放心把函数名改成一串数字。

体积还能再小吗？可以：去掉 `printf` 换成直接写系统调用，能压到 10 KB 以内。但没必要——37 KB 已经比一张图标还小。

## 九、正确性怎么保证

只有一份实现，错了也不知道。所以写了两份：

| | `lexer.c` | `lexer_参考实现.py` |
|---|---|---|
| 目的 | 快 | 好读 |
| 速度 | 502 MB/s | 1.6 MB/s |
| 行数 | 400 | 330 |
| 规则 | 同一套 | 同一套 |

两份代码对同一份源码输出的分词结果**逐字节相同**（含错误提示的行列号和文案）。一份用来跑，一份用来核对——如果哪天改了规则只改了一边，`diff` 一下立刻暴露。

```bash
./简词法 示例/词频.简 > /tmp/c.txt
python3 lexer_参考实现.py 示例/词频.简 > /tmp/py.txt
diff /tmp/c.txt /tmp/py.txt && echo "一致"
```

## 十、它不做什么

划清边界，免得你以为它漏了：

| 不做 | 为什么 |
|---|---|
| 判断语法对不对 | 那是语法分析器的事。`如果 如果 如果` 在词法层完全合法 |
| 求值 | `1 + 2` 它只切成三个词，不算出 3 |
| 展开宏 | 宏在语法树阶段处理 |
| 报告"变量没定义" | 那是语义分析的事，需要符号表 |
| 保留注释 | 注释对人有用，对编译器没用，直接扔掉 |
| 输出可逆的中间文件 | 设计上不要求可逆，所以中间产物只服务于编译，不服务于还原 |

下一步就是把这一串词喂给**语法分析器**，让它检查"关键字 标识符 符号 整数"这样的顺序合不合法，并搭出一棵语法树。
