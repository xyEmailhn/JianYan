# 第 16 章 · 并发

> 一个 `线程 { ... }` 就是一个真的新线程，不是"排个队等会儿跑"。
> 线程之间不共享变量，只共享**通道**——想递东西过去，就 `发送`。

## 16.1 完整代码

`教程/例子/15-并发.jy`：

```简言
-- 两个工人、两条线程，从同一个"活"通道领任务，把结果发到"果"通道。
-- 谁领到哪一件不固定，所以结果按件号归位再打印——
-- 并发程序只保证结果集合确定，不保证顺序。

模块 教程.并发

函数 工人(活: 通道[整数], 果: 通道[字符串]) -> 整数 {
    循环 {
        私有 可空[整数] 件 = 接收 活
        如果 件.有值 就 {
            私有 整数 值 = 件.取值()
            -- 一件成果拼成 "件号|文字"。件号写进去是为了让主线程能归位，
            -- 打印出来的是确定的那一半：谁做的看不出来，快的人会抢更多。
            发送 果, 字符串(值) .. "|" .. 字符串(值) .. " → " .. 字符串(值 * 2)
        } 否则 {
            返回 0
        }
    }
}

函数 主() -> 整数 {
    私有 通道[整数] 活 = 通道[整数](4)
    私有 通道[字符串] 果 = 通道[字符串](4)

    线程 { 工人(活, 果) }
    线程 { 工人(活, 果) }

    对 i: 1~4 {
        发送 活, i
    }
    关闭 活

    私有 映射[整数, 字符串] 收 = {}
    对 i: 1~4 {
        私有 可空[字符串] 条 = 接收 果
        如果 条.有值 就 {
            私有 字符串 组 段 = 条.取值().切分("|")
            收.插入(段[0].转整数().或默认(0), 段[1])
        }
    }
    打印行("两个工人抢 4 件活，结果按件号排好：")
    对 i: 1~4 {
        打印行(收.取(i).或默认("丢了"))
    }
    返回 0
}
```

跑一下：

```
$ 简编译 教程/例子/15-并发.jy -o /tmp/并发 && /tmp/并发
两个工人抢 4 件活，结果按件号排好：
1 → 2
2 → 4
3 → 6
4 → 8
```

具体哪件活落到哪个工人手里**不固定**，所以例子把结果按件号塞进映射、再按 1~4 打印。
并发程序只要**结果集合确定**，就不必关心谁先谁后——这条习惯能省掉大量调试。

## 16.2 通道是唯一的桥

线程之间**不能共享局部变量**。这不是限制，是设计：

```简言
私有 整数 计数 = 0
线程 {
    计数 = 计数 + 1      -- 报错：线程块里改不了外层的 计数
}
```

报错会直接告诉你怎么办：

```
线程块里改不了外层的 `计数`。线程体是独立函数，外层变量按值拷进来，改了外面看不到。
    想让它把结果带出去，就 `发送` 到通道里，外面 `接收`。
```

**为什么按值拷？** 因为线程体是一个独立的函数，它有自己的栈。外层变量是按值传进去的
（字符串、组、映射、通道在 C 里都是"头 + 指针"，拷一份头等于共享同一块内存）。
如果允许写，你写的是副本，外面永远看不到——这种"写了等于没写"比报错难查得多，
所以编译器把这种情况当错误拦下来。

**读**外层变量是允许的，也很有用：

```简言
私有 整数 基数 = 100
线程 {
    发送 报, 基数 + 1      -- 可以，拷贝一份进去
}
```

## 16.3 通道满了会等，空了也会等

```简言
私有 通道[整数] 管 = 通道[整数](2)    -- 容量 2
```

| 操作 | 通道空 | 通道有货 | 通道满 | 已关闭 |
|---|---|---|---|---|
| `发送 管, x` | 直接放进 | 直接放进 | **阻塞等**，直到有人取走 | 直接返回，什么也不做 |
| `接收 管` | **阻塞等**，直到有人送来 | 取走一个 | 取走一个 | 立刻返回 `空` |

这就是"生产者消费者"能自动调速的原因：生产者再快，也会被容量卡住；
消费者再慢，也不会让内存无限涨。

**阻塞意味着死锁是可能的**：

```简言
私有 通道[整数] 管 = 通道[整数](1)
发送 管, 1        -- 放了 1 个
发送 管, 2        -- 满了，主线程在这里永远等下去：没人接收
```

写并发程序时记住一条：**谁发送，谁就要保证有人在接收**（或者容量足够）。

## 16.4 关闭：告诉对方"没有更多了"

```简言
关闭 管
```

关闭之后：

- `接收 管` 立刻返回 `空`（不再等）——这是循环该收尾的信号；
- `发送 管, x` 静默丢弃（不报错、不崩）。

所以"读到一个通道直到没有"的标准写法是：

```简言
循环 {
    私有 可空[整数] 件 = 接收 管
    如果 件.有值 就 {
        -- 处理
    } 否则 {
        打断           -- 关了，而且已经读空
    }
}
```

`关闭` 只能由发送方调用。接收方去关，发送方会以为还能发。

## 16.5 主线程不能先走

`线程 { }` 开出来的线程是**分离态**（detached）：主线程不会等它。
主函数一返回，整个进程就退出了，还在跑的线程会被直接掐掉。

```简言
函数 主() -> 整数 {
    线程 {
        对 i: 1~1000000 { 算点东西() }
    }
    返回 0        -- 错：线程可能一个都没算完就走了
}
```

正确做法是**等一个信号**：

```简言
私有 通道[整数] 完成 = 通道[整数](1)
线程 {
    ...
    发送 完成, 1
}
私有 可空[整数] 收尾 = 接收 完成     -- 等到它说完了再往下走
返回 0
```

`后端/测试/网络.jy` 就是这么收尾的。

## 16.6 什么时候该用线程

| 场景 | 该不该开线程 |
|---|---|
| 一边算一边响应用户 | 该，典型的生产者消费者 |
| 多个互不相干的任务 | 该，结果用通道汇总 |
| 只是想让代码"看起来高级" | 不该，顺序执行更快也更好查 |
| 共享一大块数据反复改 | 谨慎，先想清楚用通道传递而不是共享 |

这一版的线程没有优先级、没有线程池、没有 `等待线程结束` 的 API。
需要"等"就用通道发个完成信号——这反而逼着你想清楚数据从哪来到哪去。

## 16.7 一个常见错误的对照表

| 写法 | 结果 |
|---|---|
| `线程 { 计数 = 计数 + 1 }` | 编译错误：改不了外层变量 |
| `线程 { 发送 报, 基数 }` | 正确，`基数` 按值拷进去 |
| 主函数不等就 `返回` | 线程被掐断，可能什么都没做 |
| 容量 1 的通道连发两次、无人接收 | 死锁（第二次发送永远等） |
| `关闭 管` 之后还 `发送` | 静默丢弃，不报错 |
| `接收` 不判断 `有值` 就 `.取值()` | 读到空值时崩（和可空一样） |

## 16.8 这一版没做的

- **真并发安全的数据共享**：没有锁、没有原子操作。要共享就用通道传，别共享。
- **线程池 / 任务队列**：每次 `线程 { }` 都是一个新 OS 线程，开销约 8 KB 栈起。
- **取消**：没有"让某个线程停下来"的办法，只能靠它自己读到关闭信号。

这三样都需要更底层的设计（内存模型、调度器、取消点），不是加几个函数能补的。
现在的边界很清楚：**线程 + 通道够写生产者消费者，不够写共享内存的多线程数据结构。**
